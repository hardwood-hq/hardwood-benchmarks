How to read these charts
Metrics
Wall, CPU and allocated are per operation; lower is better. Each point sits at the time of the commit it measured; the whiskers on wall time run from the slowest fork's mean to the fastest.
Heap after GC
The largest heap in use right after a collection in an iteration: live data plus objects promoted and not yet reclaimed. It moves with when collections fall, by as much as 40 % between runs of one commit, so a step in it means more survives a young collection only where GC time moves with it. It is not analysed for change points.
Caller share
The CPU time of the thread calling the benchmark against wall time. Near 1, that thread never waits on Hardwood, and wall time misses decode changes that CPU time still shows.
Change points
Apache Otava finds them in wall time, CPU and allocation, from a 3, 5 and 1 % change up. A regression at a commit a night measured opens an issue; one at a commit only backfills measured is drawn grey and opens none. Hover a line for the change in the history and, for a new regression, the change when both commits ran again side by side.
Epochs
A new epoch starts when what a contender measures changes, such as its preset. Each epoch has its own colour: the current one blue, superseded ones faded. Unsettled points stay off the line and out of the change-point analysis; a contender whose current epoch has not settled for 3 nights in a row is marked, and opens an issue.
Time per run
The bars beside the latest run: each nightly run, measuring in blue and gates in grey, against the dashed 60-minute target; × marks a run that recorded nothing. Backfills are left out.
Interaction
Hover a point to see its details and highlight its epoch; click it to open the report of the run that measured it. The charts open on the last 60 days of commits; All shows every recorded row. Drag across any chart to zoom every chart to that time range; Esc or Reset zoom returns.
